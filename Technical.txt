Technical Impression
Implementing Paxos in a real distributed system was a challenging and rewarding experience. Compared to the simpler 2PC protocol used previously, Paxos requires more nuanced coordination and error handling. Each replica in my system acts as a proposer, acceptor, and learner. When a client sends a PUT or DELETE request to any server, the server initiates the three Paxos phases—Prepare, Accept, and Commit—communicating with all other replicas using Java RMI. To simulate fault tolerance, each acceptor randomly fails during Prepare or Accept phases, which occasionally causes consensus to fail. This randomness helped me understand how Paxos can tolerate and recover from such transient failures as long as a majority of acceptors are functional.

Designing the internal state management for acceptors was particularly interesting. I used a thread-safe structure to track the highest promised proposal number and accepted values. To reduce livelock, each proposal uses a timestamp and atomic counter to generate a unique, increasing proposal number. While the full complexity of Paxos (like retries or view change protocols) is beyond the scope of this project, this implementation provided a strong foundation in building fault-tolerant consensus systems.

Through testing, I observed how Paxos reaches consensus under partial failure and how GET operations remain available without requiring agreement. A real-world use case of this project would be a distributed configuration service or a metadata store in a distributed file system. Overall, this assignment deepened my understanding of consensus algorithms and their practical application in resilient distributed systems. It was the most complex and insightful assignment in the series.
